    Staging and Sinks¶

    stage_file(ctx, reader, staging) connects a reader, the batch processor and the sink of the session's backend. It loads into the given staging table, respects the LoaderContext flags, returns the number of rows left in staging, and leaves the merge to the table layer.

    Load a file into the staging table.

    The reader streams the file in bounded batches, so memory does not grow with the row count. A file without data rows loads nothing and is not checked for required columns. With ctx.dedupe set, the staging table keeps the first row for each primary key. A failure after the first write rolls the session back; DuckDB commits every few batches, so earlier batches stay committed there.

    Parameters:

    Name Type Description Default
    ctx LoaderContext

    Loader context.

    		 required
    reader FileReader

    Reader that yields the file as Arrow batches.

    		 required
    staging Table

    Staging table the rows are written to.

    		 required

    Returns:

    Type Description
    int

    Number of rows left in the staging table.

    Raises:

    Type Description
    IngestError

    The file cannot be read, is missing a required column, or the rows read are not all accounted for.
    ConversionError

    A value cannot be read as its column type.
    RequiredValueError

    A required column has no value.
    RejectLimitError

    Rejected rows exceed ErrorPolicy.max_rejects.

    Interpretation¶

    • Values are interpreted by column type, as described in Conversion.
    • With the default policy an unreadable value or a missing required value raises and nothing is loaded.
    • With ErrorPolicy(on_error="reject_row") those rows, and delimited lines with the wrong number of fields, are written to <rejects_dir>/<file name>.rejects.csv and the rest load. A malformed line is listed with its row number in the file, and its text is in the reason. rejects_dir defaults to a rejects directory inside the input file's directory, and the file of an earlier load is removed. LoadReport accounts for every row read, checked against the rows counted in the staging table.
    • With normalise=False raw text is passed to the staging table unchanged, empty fields included, without literal defaults, non-key required checks or type conversion. SQL-expression defaults still apply to null staging values during merge. Primary-key columns must still be present. What the database does with a value that does not fit its column then depends on the dialect.
    • A blank value, and a column the file lacks, take the column's default when it has one: a server default written as text, a scalar Python default, or a SQL expression such as current_date. Literal defaults are converted by the column's handler. SQL expressions are applied in the merge with COALESCE, so the database evaluates them once for each row that needs a default. A column with a callable default stays required.

    Staging table¶

    Staging mirrors the target’s loadable columns and types, excluding computed columns, with no key, index, default or constraint, and a _rownum column that orders the rows (SQLite uses its rowid). Columns with SQL-expression defaults allow NULL in staging so the merge can apply their defaults. Other columns preserve the target’s nullability. Every column that is required and has no default must be in the file, primary key columns included, so a file without its key fails before anything is loaded.

    Sinks¶

    Each backend uses the fastest bulk interface its engine offers.

    Backend Sink
    PostgreSQL One COPY from Arrow-written CSV
    DuckDB Insert from a temporary view over the Arrow batch, committed every five batches
    SQLite Native executemany per batch

    A failure in the sink is raised. There is no fallback to another loading path.

    Deduplication¶

    With dedupe set, the staging table keeps the first row for each primary key, in source order. The backend removes the others after the load and reports a DedupeResult on LoadReport with the rows before and the rows removed. The merge step decides what happens when incoming rows overlap with existing target rows.

    Merge strategies¶

    Each strategy does what its name says, whatever the target already holds.

    Strategy Effect
    replace Deletes target rows whose primary key is in the file, then inserts the file
    upsert Inserts the file and skips rows whose primary key already exists, keeping the first of a repeated key
    insert Inserts the file without any key check, so a key that already exists fails with the database's duplicate key error

    insert suits a first load into an empty table, or any file whose keys are new. With dedupe=True it is several times faster than upsert, because upsert checks every row against the key index. A load with upsert into an empty table logs this hint and runs unchanged.

    With merge_batch_size set, PostgreSQL and DuckDB commit the session after each merge batch. If a later batch or deferred-key validation fails, earlier target batches stay committed, along with any other pending session work. A replace failure can leave some rows deleted or updated. SQLite keeps the batches in the caller's transaction. Use batching only when you can accept partial results and the session has no unrelated pending work.

    No schema changes are performed at the loader layer.

    Referential integrity¶

    On PostgreSQL and SQLite a load relaxes foreign keys from before it writes staging until it has merged, so the caller needs no foreign key handling and a row loaded before the row it references is accepted. SQLite ignores PRAGMA foreign_keys inside a transaction, so a session with uncommitted writes cannot start a load there and load_file raises before touching anything. To verify the result, call Table.validate_foreign_keys(session) after every table is loaded. It checks every foreign key of the table with an anti-join and raises ForeignKeyViolationError with up to five unmatched keys. Null references are not violations, and the load order does not matter.

    To insert ORM objects built in Python that reference each other, wrap the inserts in backend.relaxed_foreign_keys(session), which relaxes the keys on PostgreSQL and SQLite and leaves them enforced on DuckDB.

    Autoflush is suspended by default. Flush the pending inserts inside the block so they run while checks are relaxed:

    with backend.relaxed_foreign_keys(session):
    session.add_all(objects)
    session.flush()
session.commit()

    On PostgreSQL, relaxation is transaction-local and is reapplied when a new transaction begins, even if the session switches pooled connections. Exiting the scope restores the prior role on any transaction still active.

    DuckDB enforces the keys it creates, so load parent tables first. load_file already validates the keys DuckDB never enforces (cross-schema, cyclic and self-referential) after each table's merge, and validate_foreign_keys repeats that check, so it works the same way on every backend. A DuckDB table with foreign keys needs resolved= for both.
